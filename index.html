הפעם באמת: אוסף אמיתי על שרת Qdrant אמיתי

בשיעור 1 ראינו חצים על מפה. עכשיו יוצרים ארון תיקים אמיתי, מכניסים אליו תיקים, ומחפשים בו. כל תשובה בעמוד הזה הגיעה מהשרת, לא מסימולציה.

מה בנינו, בשלוש שורות

שרת Qdrant אמיתי (גרסה 1.19.1, חבילה חינמית, אמזון, אירופה) שמחזיק אוסף אחד בשם studio_faq. באוסף 24 משפטים של "שאלות ותשובות" מסטודיו יוגה דמיוני. זה בדיוק מה ש-מענה עושה: לקוח שואל, ומחפשים בין התשובות של העסק את המתאימה.

הציור לראש: האוסף הוא ארון תיקים. כל תיק (בשפת Qdrant: point, נקודה) מכיל שלושה דברים: מספר זהות, חץ (רשימת מספרים שמייצגת את המשמעות של המשפט), ופתק על התיק (תוספת מידע כמו נושא ושפה, נקרא payload). חיפוש = "תביא לי את התיקים שהחץ שלהם מצביע הכי קרוב לחץ של השאלה". סינון = "אבל רק מהמגירה הזאת".

צעד 1: יוצרים את הארון

הבקשה אומרת לשרת שני דברים בלבד: כמה מספרים יש בכל חץ, ואיך מודדים קרבה בין חצים.

הבקשה
PUT /collections/studio_faq
{ "vectors": { "size": 384, "distance": "Cosine" } }
התשובה האמיתית מהשרת
{
  "result": true,
  "status": "ok",
  "time": 0.144039107
}
  • 384 = כמה מספרים בכל חץ. את המספר הזה קובע מודל ההטמעה (המכונה שהופכת משפט לחץ), לא Qdrant. מודל אחר, למשל 1536 המספרים של מענה, פירושו אוסף אחר. אי אפשר לערבב.
  • Cosine = מודדים את הזווית בין החצים ולא את האורך. זה מה שראית בשיעור 1.
שימו לב מאיפה החצים: אני חישבתי אותם על המחשב שלי עם המודל החינמי paraphrase-multilingual-MiniLM-L12-v2 (384 מספרים, רב-לשוני, כרטיס המודל) ושלחתי לשרת מוכנים. Qdrant לא חישב אותם. המספרים מעוגלים ל-5 ספרות אחרי הנקודה.

צעד 2: מדפיסים תוויות על הפתקים (אינדקס)

אנחנו הולכים לסנן לפי topic (נושא) ו-lang (שפה) ו-price (מחיר). כדי שהסינון יהיה מהיר מבקשים מהשרת לבנות לכל שדה כזה "אינדקס של פתקים", כמו מפתח בסוף ספר.

PUT /collections/studio_faq/index
{ "field_name": "topic", "field_schema": "keyword" }
תשובה אמיתית
{
  "result": {
    "operation_id": 2,
    "status": "completed"
  },
  "status": "ok",
  "time": 0.103115759
}
שני דברים שלמדתי כאן מהמסמכים ומהשרת עצמו: (1) לפי מסמכי Qdrant כדאי ליצור את האינדקסים לפני שמכניסים נתונים, וכך עשיתי. (2) בשרת הזה, סינון לפי שדה שאין לו אינדקס פשוט נכשל עם שגיאה. תנסה את זה בתרגיל.

צעד 3: מכניסים תיקים (upsert)

Upsert = "תכניס, ואם כבר יש תיק עם אותו מספר, תחליף אותו". כך נראה תיק אחד, מספר 4, כשהחץ מקוצר להצגה:

{
  "id": 4,
  "vector": [
    0.04157,
    0.04555,
    -0.05001,
    -0.01271,
    -0.06871,
    "... עוד 379 מספרים ..."
  ],
  "payload": {
    "text": "שיעור ניסיון ראשון עולה 40 שקלים, ואפשר לשלם במזומן או באשראי בקבלה.",
    "topic": "price",
    "lang": "he",
    "price": 40
  }
}

הכנסתי את 24 התיקים בשלוש מנות של 8. אחרי זה ספרתי:

POST /collections/studio_faq/points/count   { "exact": true }
{
  "result": {
    "count": 24
  },
  "status": "ok",
  "time": 0.000403949
}

צעד 4: מחפשים

שולחים לשרת את החץ של השאלה ומבקשים 3 התיקים הקרובים. קודם דוגמה אחת בשלמות, אחר כך תלחץ ותראה עוד.

POST /collections/studio_faq/points/query
{ "query": [ ...384 מספרים של השאלה... ],
  "limit": 3, "with_payload": ["text","topic","lang","price"] }
השאלה: "איזה שיעורים לא מתאימים לאישה בהריון?" · תוצאה אמיתית
  • 14 0.663 classes שיעור ויניאסה דינמי לא מומלץ בהריון ולא למי שחוזרת מפציעה.
  • 13 0.653 classes שיעורי הריון מתקיימים בימי שלישי וחמישי בעשר בבוקר, בהדרכת מורה מוסמכת.
  • 15 0.378 classes יש שיעורים למתחילים לגמרי, בלי שום ניסיון קודם, בימי ראשון בשמונה בערב.

זה עובד יפה: שני התיקים הראשונים הם על הריון. המספר הכחול-כהה הוא הציון (1 = זהה, 0 = אין קשר).

עכשיו הצד הפחות מחמיא (וזה החלק החשוב)

לחץ על שאלה כדי לראות מה השרת החזיר באמת:

  • בחר שאלה למעלה.
מה שרואים (עובדות מהריצה): "בשישי" החזיר את שעות ראשון עד חמישי, והתיק הנכון (שישי עד 14:00, מספר 2) לא הגיע אפילו לשלוש הראשונות. "איך מבטלים את המנוי" החזיר ראשון הוראות על מזרן (מספר 17), והתיק הנכון על ביטול מנוי (מספר 7) לא הופיע בכלל. "חניה" החזיר ראשון את שעות הפתיחה, והחניה במקום שני.
למה (הקריאה שלי, לא עובדה מוכחת): המודל קטן וחינמי, והעברית שלו חלשה יחסית. עוד דבר: שפה אחרת עובדת טוב, ואנגלית ("can I park") מצאה את החניה בעברית כראשון, בלי תרגום. כלומר המודל מבין משמעות בין שפות, אבל לא מדויק בניואנסים של עברית. בענה אתה משתמש במודל חזק יותר (gemini-embedding-001, 1536 מספרים) ובמדרג מחדש (Voyage rerank), וזה אחד ההסברים לכך שהמדדים אצלך גבוהים בהרבה מהתוצאות כאן (לא בדקתי את זה, זו השערה). המסקנה לראיון: איכות החיפוש תלויה קודם כול במודל ההטמעה, לא במאגר. Qdrant רק מחזיק את החצים ומחשב מרחק.

צעד 5: מסננים לפי הפתקים

הפתרון הזול לטעויות כאלה: להגיד לשרת "תחפש רק בתיקים שהפתק שלהם אומר topic = cancel".

"filter": { "must": [ { "key": "topic", "match": { "value": "cancel" } } ] }

  • 12 0.180 access בכניסה יש מקלחות, ארונות נעילה ומקום להשאיר תיק.
אחרי (עם הסינון)
  • 8 0.196 cancel ביטול שיעור בודד אפשרי עד שמונה שעות לפני תחילתו, אחרת הכניסה נחשבת כמנוצלת.
  • 7 0.163 cancel אפשר לבטל מנוי בכל עת בהודעה מראש של שלושים יום, דרך הטופס באתר או בוואטסאפ.

עכשיו התיק של ביטול מנוי (מספר 7) נמצא בשלוש הראשונות, ומזרן הכושר נעלם. שים לב שהוא עדיין לא ראשון: ביטול שיעור בודד (מספר 8) קדם לו. הסינון צמצם את החיפוש, הוא לא תיקן את המודל.

איפה זה פוגש אותך (השוואה שלי, לא קוד של מענה): במענה ההפרדה בין עסקים נעשית ב-RLS של Supabase. ב-Qdrant אותו רעיון נראה כפילטר על פתק כמו business_id, ולכן אותו שדה צריך אינדקס. לפי המסמכים חיפוש וסינון נבנו לעבוד יחד.

התרגיל שלך (בערך 15 דקות)

מכאן זה אתה. הלוח למטה שולח בקשה חיה לשרת האמיתי. אתה בוחר שאלה, עורך את הבקשה ולוחץ "הרץ". השאלות הן אחת מ-11 מוכנות (כל אחת עם החץ שלה), כי החישוב של חץ לשאלה חופשית דורש מודל שלא רץ בדפדפן.

על המפתח: הלוח משתמש במפתח לקריאה בלבד, שמוגבל לאוסף studio_faq ופג תוקף אחרי 60 יום (בערך דצמבר 2026). הוא גלוי בקוד העמוד, כל מי שפותח את העמוד יכול לשאול את הארון. אי אפשר איתו לשנות או למחוק (יש כפתור שמוכיח את זה בשלב 6). הנתונים בארון הם משפטים דמיוניים.

    ש: מה ההבדל בין collection, point ו-payload?
    תשובה

    קצר: collection = אוסף, point = רשומה אחת עם חץ, payload = נתונים נלווים על הרשומה.
    מושג: החיפוש הוא על החצים; הפתקים משמשים לסינון ולהצגה.
    לזכור: ארון, תיק, פתק.
    

    ש: למה יוצרים payload index, ומתי?
    תשובה

    קצר: כדי שסינון יהיה מהיר. לפני הכנסת הנתונים, לפי המסמכים.
    מושג: חיפוש וקטורי לבד לא מספיק כשיש סינון, צריך גם אינדקס רגיל על השדות. בשרת שלנו סינון בלי אינדקס נכשל.
    לזכור: מפתח בסוף ספר.
    

    ש: החיפוש החזיר תשובה שגויה. האם Qdrant אשם?
    תשובה

    קצר: כנראה לא. קודם כול מודל ההטמעה.
    מושג: Qdrant מחזיק חצים ומחשב מרחק. מה שהחץ אומר נקבע במודל. מתקנים עם מודל טוב יותר, מדרג מחדש, וסינון.
    לזכור: השרת לא מבין עברית, המודל מבין.
    

    ש: למה indexed_vectors_count הוא 0 ועדיין החיפוש עובד?
    תשובה

    קצר: בכמות קטנה השרת עובר על הכול.
    מושג: full_scan_threshold: מתחת לסף אין טעם בגרף HNSW.
    לזכור: לחפש בשלושה תיקים אין צורך במפה.
